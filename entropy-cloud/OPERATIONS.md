# Фонове оновлення Entropy

Ціль — твіти про Entropy через twitterapi.io: прямі згадки @entropyIO, офіційні посилання й контекстні збіги назви. Працювати лише з цим закритим Site; не змінювати його доступ, ключ, формулу або модерацію під час звичайних запусків. Невпевнені збіги не підтверджувати автоматично: вони залишаються в приватній черзі перевірки.

Основний погодинний запуск перевіряє свіжі пости окремо в усіх трьох напрямах: `direct`, `evidence` і `context`. Спочатку кожний напрям отримує власний запит до найновішого вікна; лише потім обмежено продовжуються його свіжі сторінки. Історичні вікна й метрики не займають ці місця. Дивитися `sync.hourly.lanes[напрям].latestSuccessAt`, `latestError`, `latestNextRunAt` та `collectionHealth.lanes`; загальний `lastSuccessAt` може стосуватися історії або метрик.

У поточному розгортанні є два пов’язані хмарні завдання в часовому поясі Europe/Warsaw:

- На 35-й хвилині кожної години основне завдання `Automation_a6b7f4d21b0c8191aa27cf4d55711676` викликає `entropy_sync` або один POST з `{}`, потім читає статус. Обидва входи виконують той самий серверний цикл перевірки всіх трьох напрямів. Розклад не залежить від відкритої сторінки.
- На 45-й хвилині кожної години допоміжне завдання `Automation_da1edb2e9f348191b6dd92897a523df5` спочатку читає статус. Воно працює лише після успішного свіжого пошуку не давніше 90 хвилин: до 6 сторінок продовження й один пакет метрик. Воно ніколи не надсилає POST з `{}` і не дублює свіжий пошук.

Наведені нижче кроки описують протокол обох завдань; основне виконує свіжий пошук, допоміжне — тільки окремі maintenance-дії.

1. Отримати актуальний `get_site` для Site ID із пов’язаного завдання. Переконатися, що доступ owner-only і є живий URL. Якщо доступ став ширшим, зупинитися та повідомити власника.
2. Отриманий `siwc_bypass_bearer_token` використовувати лише для цього ж Site в заголовку `OAI-Sites-Authorization: Bearer <token>`. Значення не друкувати, не зберігати в файлах і не копіювати в підказку завдання.
3. Основне завдання викликає `entropy_sync` або один `POST <live_url>/internal/sync` з `Content-Type: application/json`, `X-Entropy-Update: 1` і тілом `{}`. Сервер окремо перевіряє дозволений час для кожного напряму. Цикл обмежений дев'ятьма запитами й приблизно100секундами; окремий запит має дедлайн25секунд. Для приватного HTTP-виклику дозволити120секунд очікування. Якщо клієнт завершив очікування раніше, перечитати статус і збережений результат; не повторювати запуск наосліп. Допоміжне завдання цей POST пропускає й починає з GET.
4. Прочитати `GET <live_url>/internal/sync`. Перевіряти `collectionHealth.allLanesCurrent`, `collectionHealth.lanes` і `sync.hourly.cycle`. Запис циклу містить ID, час, транспорт виклику, кількість запитів і результат кожного напряму. `source: mcp` або `service` позначає транспорт, а не доводить автоматичне походження; для цього потрібна історія виконання планувальника. Успішний свіжий пошук не гарантує вичерпання всіх сторінок. Якщо збір вимкнений, призупинений, ще не настав дозволений час або є помилка — не вмикати, не форсувати й не обходити обмеження.
5. Допоміжне завдання на 45-й хвилині перевіряє, що `sync.hourly.lastSuccessAt` не старіше 90 хвилин. Лише після успішної перевірки найновішого вікна воно може виконати до 6 додаткових `POST` із тілом `{ "action": "catchup" }`, якщо `sync.hourly.pendingWindows` не порожня. Один такий виклик продовжує одну сторінку, з власним збереженим курсором. Між кроками чекати до `nextAttemptAt`/`catchupNextAttemptAt`; сервер додатково забезпечує щонайменше5,1секунди. Зупинитися при помилці, паузі, відсутній черзі, HTTP429, досягненні шести кроків або граничного часу завдання. Незавершені сторінки залишаються на наступний запуск.
6. Допоміжне завдання після успішного свіжого пошуку й обмеженого продовження може виконати не більше одного `POST` із тілом `{ "action": "metrics" }`. Воно ніколи не підміняє це дією `{}`. Пакет оновлює до20давніше перевірених постів, має окремий погодинний час і стан `sync.metricsRefresh`. При тайм-ауті пакет зменшується до10, потім до5; невдалі ID повертаються в кінець черги без втрати попередніх лічильників. Помилка метрик не відкладає наступний свіжий пошук.
7. Прочитати фінальний статус. Не розгортати Site повторно й не змінювати ручні рішення. Кожен POST має окремий lease120секунд і резервує одну денну спробу до запиту провайдера. `sync.collectorBusyUntil` — безпечний час завершення поточного lease; його токен ніколи не повертається. HTTP423 означає зайнятий запис; не запускати паралельні платні кроки. За потреби дочекатися звільнення в межах часу завдання й перечитати статус перед новою спробою.

Маршрут `/internal/sync` покладається на документовану закриту межу Sites для unattended service access. Він не призначений для публічного Site. Browser API додатково вимагає підтверджену особу; сервісний токен не слід підміняти заголовками особи.

Основний погодинний запуск відведений свіжим згадкам усіх трьох напрямів. Старі сторінки й метрики виконує окреме допоміжне завдання. Спільний серверний ліміт — 288 спроб на добу UTC, включно з помилками. Історія, метрики, точкове відновлення й старий дозбір мають фіксований поріг 216 загальних спроб. Лише пагінація свіжого інтервалу може використати вищий динамічний поріг: вона залишає по три спроби на кожний майбутній запуск о xx:35 до наступної півночі UTC, максимум 72. `collectionHealth.freshPaginationReserve` показує залишений резерв, а `freshPaginationDailyLimit` — поріг `288 - резерв` на спільному лічильнику. Це не додатковий бюджет і не послаблення ліміту для історії чи метрик. Обмеження циклу не є обіцянкою витрачати дев'ять запитів щогодини. Невідомі або відсутні метрики не стають нулями.

Погодинні завдання запускаються о xx:35 і xx:45. Після успішної свіжої перевірки `latestNextRunAt` узгоджується з наступною35-юхвилиною: ручна перевірка до неї не скасовує найближчий автоматичний запуск. Це найраніший дозволений сервером час, а не гарантія точного виконання зовнішнього завдання. Помилки й обмеження провайдера зберігають свої окремі дедлайни повтору. Перед зміною розкладу перечитувати пов’язані automations через get_site й узгоджувати серверну константу `HOURLY_SCHEDULE_MINUTE`, зберігаючи обидві ролі без дублювання свіжого пошуку.

Окремий прискорений історичний прохід створюється лише явним запитом власника через `/internal/backfill`. Звичайний `/internal/sync` не продовжує його замість нових згадок, не створює новий прохід, не збільшує requestLimit і не відновлює `paused` або `request-limit` черги. Успішне вичерпання пошуку провайдера не гарантує наявності всіх постів на X; пропуски й аномалії залишаються в статусі.

Підтримуваний планувальник тут — пов’язані хмарні завдання Sites з автономним сервісним доступом. Наявність прямого Worker cron-handler цим проєктом не заявляється. Створення або увімкнений стан розкладу самі не доводять, що запит виконався: перед передачею потрібно перевірити writer й readback через цей самий приватний HTTP-маршрут.

## Публічний Vercel-фронтенд

Публічна адреса — [entropy-leaderboard.vercel.app](https://entropy-leaderboard.vercel.app). Це окремий інтерфейс `entropy-vercel/` з фіксованим проксі лише до вже публічного `/api/leaderboard` на існуючому Site. У Vercel немає окремої бази, ключів провайдера або розкладу; приватний збір і модерація залишаються тут. Першу версію завантажено папкою, бо з’єднання GitHub було недоступне: автоматичне розгортання коду з GitHub не налаштоване. Дані оновлюються через існуючу публічну проєкцію незалежно від оновлень коду. Публічний `lastDiscoveryAt` залишається часом прямого напряму; стан усіх трьох перевіряється у приватних `collectionHealth.lanes`, `allLanesCurrent` і записі циклу.
